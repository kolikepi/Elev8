====================================================
CORE BUSINESS PRINCIPLE
====================================================

ForwardOne must separate:

QUOTE DATA

from

BOOKING DATA

from

ACTUAL SHIPMENT DATA.

A customer requesting a quotation should NOT be required to provide every
operational booking detail.

The complete and exact operational information should be collected AFTER
the customer accepts the quotation.

Customer UX must follow:

SIMPLE OUTSIDE — POWERFUL INSIDE.

The customer should see plain language and minimal mandatory fields.

Technical logistics complexity belongs in the administrator workspace.

====================================================
1. QUOTE REQUEST VS BOOKING
====================================================

Do not redesign the existing Quote Request workflow in this phase.

Preserve the existing quote form and pricing flow.

The quotation stage should continue to collect only information required
to prepare the quotation.

Full sender/receiver operational details must NOT become mandatory merely
to request a quotation.

After a customer accepts a quotation:

DO NOT immediately treat the shipment as fully bookable.

The customer-facing state should become:

Accepted — Complete Booking Details

Internally create/use an appropriate booking-details-required state without
breaking existing status compatibility.

Display a clear CTA:

Complete Booking Details

====================================================
2. POST-ACCEPTANCE BOOKING DETAILS
====================================================

Create a dedicated customer booking-details workflow.

Existing data from the accepted quote MUST be prefilled.

Never force the customer to enter the same information twice.

The customer should:

Review existing information
→ Complete missing operational information
→ Confirm booking details

Use progressive disclosure and conditional fields.

Do NOT show one giant logistics form.

====================================================
3. EXPRESS BOOKING DETAILS
====================================================

For Express Courier shipments such as:

FedEx Express
TNT Express
TNT Economy
DHL Express

collect the complete operational data after acceptance.

Sender / Pickup:

- Company or sender name
- Full pickup address
- Country
- City
- Postal code
- Contact person
- Phone
- Email where appropriate
- Pickup / ready date
- Pickup instructions where applicable

Receiver / Delivery:

- Company or receiver name
- Full delivery address
- Country
- City
- Postal code
- Contact person
- Phone
- Email where appropriate

Shipment confirmation:

- Number of pieces
- Package types
- Final dimensions for every piece
- Final actual weight for every piece
- Contents description
- Commercial or personal shipment
- Commercial value where applicable
- Currency
- Incoterm where applicable
- Customer reference / PO where applicable

Documents should be requested only when applicable.

Examples:

Commercial Invoice
Packing List
MSDS
DG documentation
other required customs documents

Do not make irrelevant documents mandatory.

====================================================
4. ROAD / GROUPAGE BOOKING DETAILS
====================================================

For Road Freight / Groupage / LTL / pallet shipments, additionally support:

- Full loading address
- Full unloading address
- Loading contact
- Delivery contact
- Opening hours
- Requested loading date/time
- Pallet information
- Stackable Yes/No
- Forklift available Yes/No
- Tail-lift required Yes/No
- Loading requirements
- Unloading requirements
- Customer reference
- Supplier reference
- Special instructions

Only display these fields when applicable.

====================================================
5. PREFILL & DATA SEPARATION
====================================================

Booking Details must start from the accepted quotation data.

However:

DO NOT overwrite the accepted quotation data.

Store the final booking information separately or version it appropriately.

The system must be able to distinguish later between:

Quoted Data
Booked Data
Actual Carrier Data

Example:

Quoted weight: 40 kg
Booked weight: 43 kg
Actual carrier weight: 47 kg

All three values must eventually be able to coexist.

====================================================
6. CHANGE IMPACT ENGINE
====================================================

When the customer submits Booking Details, compare:

Accepted Quotation Data

against

Final Booking Data.

Classify changes into:

NO_PRICE_IMPACT

RECALCULATION_REQUIRED

MANUAL_REVIEW_REQUIRED

Examples:

NO_PRICE_IMPACT:
- Contact name
- Phone number
- Email
- Minor pickup instructions
- Opening hours

RECALCULATION_REQUIRED:
- Weight
- Dimensions
- Number of pieces
- Package type
- Origin/destination postal code when pricing may depend on it
- Origin/destination location when pricing changes
- Service-related cargo characteristics

MANUAL_REVIEW_REQUIRED:
- Dangerous Goods status change
- Commodity/content change that may affect eligibility
- Customs-sensitive changes
- special handling changes
- any condition where automatic pricing cannot safely determine impact

Do NOT silently change the accepted quotation.

====================================================
7. RECALCULATION & needsReapproval
====================================================

Reuse the EXISTING:

- pricing engine
- recommendation engine
- volumetric rules
- tariff engine
- surcharge engine
- needsReapproval mechanism

Do NOT build parallel calculation logic.

If Booking Details change pricing-relevant data:

1. Mark the booking for review.
2. Recalculate suggested carrier/service costs where possible.
3. Set needsReapproval when appropriate.
4. Block final booking until the issue is resolved.

If no exact automatic rate exists:

Manual Review Required

Do not invent a price.

====================================================
8. CUSTOMER UX
====================================================

Customer-facing language must remain extremely simple.

Do not expose internal status names such as:

BOOKING_DETAILS_REQUIRED
RECALCULATION_REQUIRED
MANUAL_REVIEW_REQUIRED

Translate them into human-friendly UI.

Examples:

"Complete your shipment details"

"We're reviewing an update to your shipment"

"Your updated shipment details may affect the quotation"

"Action required"

At every stage the customer should understand:

1. What is happening?
2. What do I need to do?
3. What happens next?

====================================================
9. ADMIN BOOKING REVIEW

Create or extend the existing Admin Quote/Booking view.

ORIGINAL ACCEPTED QUOTE

versus

FINAL BOOKING DETAILS

Highlight changed fields.

Example:

Weight

Do not expose this internal comparison to customers except for information

====================================================
10. READY FOR BOOKING
====================================================

A shipment may become:

READY FOR BOOKING

only when:

- latest quotation is accepted
- booking details are complete
- required documents are complete
- no pricing reapproval is pending
- no unresolved manual review blocks booking
- existing Booking Checklist requirements are satisfied

Reuse and extend the EXISTING Booking Checklist.

Do not create another checklist system.
